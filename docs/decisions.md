# Decisions

One line per decision where the specification is silent or had to be adjusted.

- Comments in the runtime sources are translated to English; the code is otherwise verbatim from the specification.
- Statements end at a newline or `;`. A call `(` and a binary `+`/`-` must be on the same line as the token before them, otherwise they start a new statement.
- Operator precedence follows Kotlin: `?:` binds tighter than comparisons and looser than `+`/`-`. `?:` is right-associative, so `a ?: b ?: c` evaluates `c` only when `a` and `b` are null.
- `==` and `!=` are emitted as Java `==` and `!=` (reference equality for objects), keeping the translation one to one.
- An unqualified call of a capitalized name that is not a declared or imported function is a constructor call: `Foo(x)` becomes `new Foo(x)`, and so does one qualified by a package: `java.sql.Timestamp(1L)`. Type arguments are written explicitly: `Foo<String>()` or `Foo<>()`. Only `Ok` and `Err` get the diamond automatically.
- `?.` wraps the rest of its call chain: `a?.b().c()` becomes `Nulls.map(a, $n1 -> $n1.b().c())`, so the first null skips the whole tail.
- A safe call chain used as a statement expands to `final var $n1 = a; if ($n1 != null) { ... }` instead of `Nulls.map`, so `listener?.onEvent(x)` works with void methods.
- Lambdas are written `{ x, y -> body }`. `{ body }` takes no parameters, unless the body uses `it` and no `it` is in scope; then `it` is its parameter. `{ -> body }` always takes no parameters. A lambda with several statements returns its value with an explicit `return`.
- `var` declares a mutable local (`var x = 0` becomes `var x = 0;`); `=`, `+=`, `-=`, `*=`, `/=` and `%=` are assignment statements. Parameters and `val`s cannot be assigned (AXL008).
- Copies of captured `var`s are named `$c1`, `$c2`, ... A `while` whose condition needs copies becomes `while (true) { copies; if (!(cond)) break; ... }`; an `else if` that needs copies becomes `else { copies; if ... }`.
- `fn f() = try g()` in a function without a result type is the statement form of `try`; in a function with a result type it is `return try` (AXL005). `try` in a top-level `val` is AXL007.
- `private val` is allowed at top level and becomes `private static final`.
- Java keywords cannot be used as names (AXL011); the file name must be a valid Java class name (AXL012).
- `fn main()` means a function named `main` with no parameters and no result type.
- javac diagnostics are reported at the .axl column of the name javac points at, found by matching that name in the .axl line (counted from the end of the line); without a match, at the first non-blank column. Multi-line javac messages are joined with `; `, and identical diagnostics on one .axl line are reported once.
- Generated classes have no blank lines between members, as in the specification example.
- `axl build` writes generated sources to the `-d` directory unless `-s` is given, like javac. `axl run` compiles the whole source root, which it derives from the file path and its package.
- NullAway runs with `JSpecifyMode=true` and `OnlyNullMarked=true`, which replaces `AnnotatedPackages`; every generated class is `@NullMarked`.
- Error Prone runs inside the compiler's JVM, so the CLI and the tests start with `--add-exports`/`--add-opens` for `jdk.compiler`; `--no-null-checks` turns the checks off.
- NullAway messages other than dereferences are shown without the `[NullAway]` prefix and link; dereferences get their own message (AXL102).
- `--inline-elvis` is implemented although the benchmark shows no measurable cost (see [performance](perf.md)), because the build plugins expose it. It expands only a `?:` at the root of an initializer, assignment or `return`, and the temporary shares the `$t` counter.
- The Gradle task is named `generateAxl` (`generateTestAxl` for tests) instead of `generateBrod`.
- Errors of `compileJava` are moved to `.axl` files by a javac plugin (`-Xplugin:AxlDiagnostics` from `axl-compiler-javac`) rather than by intercepting task output; see [the Gradle plugin](gradle.md).
- Error Prone and NullAway are runtime dependencies of the CLI only, so that `axl-compiler-javac` on an annotation processor path does not bring a second copy of them.
- Functional tests of build plugins resolve Axolotl artifacts from `build/test-repo`, which every published module also publishes to.
- `axl-maven-plugin` and `axl-archetype-quickstart` are Maven projects (annotations, invoker and archetype tooling are Maven-native); the Gradle build runs them with the Maven wrapper in `axl-maven-plugin/` as part of `check`.
- Maven shows `.axl` positions during `compile` through the same javac plugin as Gradle; `axl:generate` passes its arguments in the property `axl.javacPlugin`. `axl:check` is a standalone goal that compiles again and prints `.axl` positions, since a goal cannot run after a failed `compile` in the same build.
- Error Prone is loaded from the class loader of `axl-compiler-javac` when it is a `URLClassLoader` (a Maven plugin realm), otherwise from `java.class.path`.
- Parentheses around `?:`, `?.` and `attempt` are dropped in the generated Java, where they expand to method calls; Error Prone would flag them as unnecessary.
- The SMAP's default stratum is `Java`, not `Axolotl`, so debuggers without Axolotl support keep showing the generated `.java` lines.
- In Gradle the SMAP is added by a last action of `compileJava` rather than by a separate task, so the classes stay outputs of one task and are cached with their SMAP.
- Failing tests are retraced by a JUnit Jupiter extension (`TestExecutionExceptionHandler`) loaded through extension autodetection, not by a `TestExecutionListener`: JUnit notifies listeners of finished tests in reverse order, so Gradle's and Surefire's own listeners would record the failure first. The same extension works for Maven, instead of a Surefire reporter.
- Retraced stack frames drop the class loader name, which a new `StackTraceElement` would otherwise print even for the built-in `app` loader.
- The language server uses full document synchronization and serves every request on one thread; while a line is incomplete, completion and navigation use the last version of the file that parsed.
- Member completion knows the receiver's type when it is a class name, a name with a written type, or a local whose type javac infers in the generated code; longer call chains are not completed.
- The VS Code extension bundles the server's jars (`server/lib`) and starts it with the JDK from `axl.java.home`, `JAVA_HOME` or the PATH.
- The IntelliJ plugin uses a hand-written `PsiBuilder` parser over the ANTLR lexer instead of an ANTLR-to-PSI adaptor, for error recovery while typing.
- Java sees `.axl` files through light classes whose member types come from the in-memory translation parsed as Java; members navigate to the `.axl` declarations.
- javac and NullAway errors in IntelliJ come from `axl check` run in a separate JVM (the IDE's JVM lacks the options Error Prone needs) and appear after a save; in Ultimate the language server reports them instead.
- In Ultimate the language server provides diagnostics and hover only; completion, navigation and highlighting stay with the plugin's PSI so that the two do not duplicate each other.
- The platform has no extension point to hide local variables in the debugger, so the translator's `$` locals are labeled "Axolotl internal" instead of hidden.
- `fn main()` runs through IntelliJ's Java application run configuration for the generated class; building is left to Gradle or Maven delegation.
- The project builds with Gradle 9; the Gradle plugin it publishes still supports Gradle 8.5 and newer, which a functional test checks.
- `try` binds like a unary operator (`try a + try b` is `(try a) + (try b)`); in stage 1 it took the whole expression to its right, which made no difference in the two statement forms allowed then.
- Lifted `try`: operands to its left that are not literals, lambdas or the file's own names are kept in `$t` temporaries; `&&`/`||` with `try` on the right become `boolean $t = false; if (left) { ... }`, so that a null check on the left still covers the right, and an `if (a && try b)` without `else` becomes nested `if`s; `?:` becomes `T $t = left; if (Objects.isNull($t)) { ... }`, with `T` from the written type of the `val` or the function when there is one; a `while` condition is evaluated inside `while (true)`.
- `try` after `?.` stays an error: the expansion would need the rest of the chain inside a conditional, and moving the `try` into a `val` is clearer.
- Pipes support `filter`, `map`, `peek`, `sorted`, `distinct`, `limit`, `skip`, `forEach`, `anyMatch`, `allMatch`, `noneMatch`, `count`, `first` and `mapResult`; without an ending stage the result is `toList()`. A lambda of a stage without parameters takes `it` even if the body does not use it.
- `mapResult` expands to a loop over a `$p` list. The runtime has no helper and the translator no types, so the element type comes from the `val`'s written `List<T>` or from a same-file function returning `Result<T, E>` (AXL009 otherwise).
- `a!!` expands to `java.util.Objects.requireNonNull(a)`, so the exception points at the assertion and NullAway treats the result as non-null.
- Top-level `val` types are inferred in two steps: local rules for literals, operators, constructor calls and same-file functions; for the rest, javac attributes a `$infer` method in a draft translation of the whole module (unknown types replaced by `Object`) and the inferred type is written into the generated field. Generated Java never contains `var` at class level.
- NullAway trusts JDK generics: it does not check what a lambda returns to a JDK functional interface, the `?` of type arguments such as `List<String?>`, or the declared types of locals. A javac `TaskListener` started by the `AxlDiagnostics` plugin (`NullChecker`) checks these in generated classes; it reports only what NullAway cannot see, so one problem gives one error. javac drops type annotations when it infers types, so the checker follows the `?` of type arguments through `var` locals, `new` and stream calls by itself. Its reports wait for the end of the compilation, because Error Prone skips its analysis once there are errors.
- The JDK's functional interfaces say nothing about null, so a lambda passed to one may not return null unless the type argument has `?`; `Map.computeIfAbsent` and the other `Map` methods allow it for a value type with `?`, and `Optional.map` always does.
- Strict null mode is off by default: without it the rules match NullAway's, which trusts unannotated code. The same checker does it (plugin argument `strict`) and checks only generated classes, so mixed Java sources are unaffected.
- Strict mode trusts JDK constants (`System.out`), constants, the Axolotl runtime, `Objects.requireNonNull*`, string, number and `Math` methods, the immutable collection factories, `toString()`, `@NullMarked` code and members annotated `@NonNull`/`@NotNull`/`@Nonnull`; everything else returned from Java is nullable until checked. A lambda kept in a value of a JDK interface type gets nullable parameters, since any Java code may call it. Narrowing follows the same rules as NullAway: `!= null`/`== null` checks, `&&`, `||`, early exits, `while` conditions; a loop body is scanned until the nullable values it leaves settle.
- javac's most common messages (unknown names, type mismatches, wrong arguments, missing returns) are reworded with Axolotl type names; the rest are shown as javac prints them. NullAway's nullable argument message becomes AXL102 like a dereference.
- The Maven build of the plugin removes `org/axl` from its build-local repository first, because Maven would otherwise keep using the copies of the modules it resolved in an earlier build.
- The runtime is `@NullMarked`, so NullAway checks the value types of `Result`: `Ok(null)` does not fit `Result<String, E>`. `Result.mapErr` converts the error type for `try`.
- `a ?: b` passes its fallback as `Nulls.Fallback`, a null-marked interface, because NullAway does not check what a lambda returns for JDK interfaces such as `Supplier`; a number on the right is passed directly (`Nulls.or(a, 0)`) so that Java widens it to `Long` or `Double`, with overloads for primitive, boxed and other (`Number`, `Object`) left sides. After `?.` the left side is moved into a temporary first, so that Java can type it. With `--inline-elvis`, a `?:` between two different kinds of boxed numbers keeps the `Nulls.or` form, because Java would unbox both sides of the conditional.
- A pipe's `map` lambda is wrapped in `Nulls.nonNull`, which makes NullAway reject a `map` that may produce null; the lists pipes build cannot hold nulls.
- A `?.` chain passed as an argument is moved into a temporary first: as an argument, the result type of `Nulls.map` would come from the parameter, which makes overloads such as `println` ambiguous. Where no statement can go (one-line lambdas, top-level values, `attempt`), it is passed as `Nulls.typed(...).value()`, whose receiver Java types before it picks an overload.
- `|> first` is `Nulls.first(stream.iterator())`: `findFirst` throws on a null element, and an iterator argument keeps the call out of overload resolution.
- Operands to the left of a lifted `try` keep Java's order, including the receiver of a call, the receiver of a method reference, the object of an assigned field and the value a compound assignment reads; class and package names (also nested ones such as `Thread.State`) are not copied, and `Ok(x)`, `Err(x)`, diamonds and factories such as `List.of(...)`, `Optional.empty()` and `Comparator.naturalOrder()` stay inline with their arguments copied, so that Java infers their type arguments.
- A stage lambda nested in another lambda that has `it` is an error (AXL004): Java forbids a lambda parameter that shadows another, and renaming `it` would surprise readers.
- `java` and `axl` cannot name locals or files, `System`, `Nulls` and `Result` cannot name values, and `args` cannot name a local of `fn main()` or a top-level value of its file, because the generated code uses them; files cannot be named after the classes the generated code uses (`Nulls`, `Result`, `Ok`, `Err`, `System`, `Nullable`, `NullMarked`, `String`, `Integer`, `Long`, `Double`, `Boolean`, `Object`, `Exception`).
- Generated Java keeps the line breaks of long expressions, so each operand, argument, chain step and pipe stage maps to its own .axl line.
- Top-level values are checked for reads of later values, also through functions of the file, lambdas and function references passed to calls, values that hold a lambda, and `Main.x` (AXL016), because they are static fields set in order. Values of two files that read each other are reported by the javac plugin, which sees all classes.
- In a call `a < b, c > (d)` is read as two comparisons unless the names between `<` and `>` look like types (start with a capital letter).
- Incremental builds translate again every file with inferred top-level values whenever any file changes; Maven keeps its state in `target/axl/*.state.json` and redoes everything when options, the plugin, the classpath or the Java sources change. Both read all files on every build to reject duplicate classes.
- The parser tries SLL prediction first and falls back to LL only for input SLL cannot handle; the line predicates made LL prediction quadratic on long expressions.
- `axl run` lets the program's other threads finish instead of calling `System.exit` after `main`. Its work directory stays while the program runs, because a shutdown hook would race the program's own hooks; the next `axl run` removes the directories whose lock file is free.
- macOS packages carry the major version plus one (0.1.0 is packaged as 1.1.0, 1.0.0 as 2.0.0): jpackage rejects a bundle version that starts with 0, and keeping the offset after 1.0 keeps bundle versions growing, so that the installer never takes a newer release for an older one. The file name of the package and `axl --version` show the real version.
