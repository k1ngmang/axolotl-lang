# Decisions

One line per decision where the specification is silent or had to be adjusted.

- Comments in the runtime sources are translated to English; the code is otherwise verbatim from the specification.
- Statements end at a newline or `;`. A call `(` and a binary `+`/`-` must be on the same line as the token before them, otherwise they start a new statement.
- Operator precedence follows Kotlin: `?:` binds tighter than comparisons and looser than `+`/`-`. `?:` is right-associative, so `a ?: b ?: c` evaluates `c` only when `a` and `b` are null.
- `==` and `!=` are emitted as Java `==` and `!=` (reference equality for objects), keeping the translation one to one; on strings, data classes and other values with their own `equals` they are an error (Error Prone's ReferenceEquality), since such a comparison is never meant and compiled wrong programs.
- An unqualified call of a capitalized name that is not a declared or imported function is a constructor call: `Foo(x)` becomes `new Foo(x)`, and so does one qualified by a package: `java.sql.Timestamp(1L)`. Type arguments are written explicitly: `Foo<String>()` or `Foo<>()`. Only `Ok` and `Err` get the diamond automatically.
- `?.` wraps the rest of its call chain: `a?.b().c()` becomes `Nulls.map(a, $n1 -> $n1.b().c())`, so the first null skips the whole tail.
- A safe call chain used as a statement expands to `final var $n1 = a; if ($n1 != null) { ... }` instead of `Nulls.map`, so `listener?.onEvent(x)` works with void methods.
- Lambdas are written `{ x, y -> body }`. `{ body }` takes no parameters, unless the body uses `it` and no `it` is in scope; then `it` is its parameter. `{ -> body }` always takes no parameters. A lambda with several statements returns its value with an explicit `return`.
- `var` declares a mutable local (`var x = 0` becomes `var x = 0;`); `=`, `+=`, `-=`, `*=`, `/=` and `%=` are assignment statements. Parameters and `val`s cannot be assigned (AXL008).
- Copies of captured `var`s are named `$c1`, `$c2`, ... A `while` whose condition needs copies becomes `while (true) { copies; if (!(cond)) break; ... }`; an `else if` that needs copies becomes `else { copies; if ... }`.
- `fn f() = try g()` in a function without a result type is the statement form of `try`; in a function with a result type it is `return try` (AXL005). `try` in a top-level `val` is AXL007.
- `private val` is allowed at top level and becomes `private static final`.
- Java keywords cannot be used as names (AXL011); the file name must be a valid Java class name (AXL012).
- `fn main()` means a function named `main` with no parameters and no result type.
- javac diagnostics are reported at the .axl column of the name javac points at, found by matching that name in the .axl line (counted from the end of the line); without a match, at the first non-blank column. Multi-line javac messages are joined with `; `, and identical diagnostics on one .axl line are reported once.
- Generated classes have no blank lines between members, as in the specification example.
- `axl build` writes generated sources to the `-d` directory unless `-s` is given, like javac. `axl run` compiles the whole source root, which it derives from the file path and its package.
- NullAway runs with `JSpecifyMode=true` and `OnlyNullMarked=true`, which replaces `AnnotatedPackages`; every generated class is `@NullMarked`.
- Error Prone runs inside the compiler's JVM, so the CLI and the tests start with `--add-exports`/`--add-opens` for `jdk.compiler`; `--no-null-checks` turns the checks off.
- NullAway messages other than dereferences are shown without the `[NullAway]` prefix and link; dereferences get their own message (AXL102).
- `--inline-elvis` is implemented although the benchmark shows no measurable cost (see [performance](perf.md)), because the build plugins expose it. It expands only a `?:` at the root of an initializer, assignment or `return`, and the temporary shares the `$t` counter.
- The Gradle task is named `generateAxl` (`generateTestAxl` for tests) instead of `generateBrod`.
- Errors of `compileJava` are moved to `.axl` files by a javac plugin (`-Xplugin:AxlDiagnostics` from `axl-compiler-javac`) rather than by intercepting task output; see [the Gradle plugin](gradle.md).
- Error Prone and NullAway are runtime dependencies of the CLI only, so that `axl-compiler-javac` on an annotation processor path does not bring a second copy of them.
- Functional tests of build plugins resolve Axolotl artifacts from `build/test-repo`, which every published module also publishes to.
- `axl-maven-plugin` and `axl-archetype-quickstart` are Maven projects (annotations, invoker and archetype tooling are Maven-native); the Gradle build runs them with the Maven wrapper in `axl-maven-plugin/` as part of `check`.
- Maven shows `.axl` positions during `compile` through the same javac plugin as Gradle; `axl:generate` passes its arguments in the property `axl.javacPlugin`. `axl:check` is a standalone goal that compiles again and prints `.axl` positions, since a goal cannot run after a failed `compile` in the same build.
- Error Prone is loaded from the class loader of `axl-compiler-javac` when it is a `URLClassLoader` (a Maven plugin realm), otherwise from `java.class.path`.
- Parentheses around `?:`, `?.` and `attempt` are dropped in the generated Java, where they expand to method calls; Error Prone would flag them as unnecessary.
- The build step after `javac` rewrites `SourceFile` and the `LineNumberTable` of generated classes to the `.axl` file and lines, so plain stack traces and debuggers name `.axl` positions; generated lines without a mapping take the closest mapped line above them, and code with none above gets no line. The SMAP's default stratum stays `Java`, which now is the `.axl` position, and the stratum `Axolotl` maps each `.axl` line to itself. The existing `smap` switch turns the whole step off; there is no option for the SMAP without the rewrite, since the two have to agree.
- Lambda bodies keep javac's names (`lambda$main$0`) in stack traces: renaming them would mean rewriting the bootstrap arguments of every `invokedynamic`, for a name that users read only as "inside a lambda of `main`".
- In Gradle the SMAP is added by a last action of `compileJava` rather than by a separate task, so the classes stay outputs of one task and are cached with their SMAP.
- Failing tests are retraced by a JUnit Jupiter extension (`TestExecutionExceptionHandler`) loaded through extension autodetection, not by a `TestExecutionListener`: JUnit notifies listeners of finished tests in reverse order, so Gradle's and Surefire's own listeners would record the failure first. The same extension works for Maven, instead of a Surefire reporter.
- Retraced stack frames drop the class loader name, which a new `StackTraceElement` would otherwise print even for the built-in `app` loader.
- The language server uses full document synchronization and serves every request on one thread; while a line is incomplete, completion and navigation use the last version of the file that parsed.
- Member completion knows the receiver's type when it is a class name, a name with a written type, or a local whose type javac infers in the generated code; longer call chains are not completed.
- The VS Code extension bundles the server's jars (`server/lib`) and starts it with the JDK from `axl.java.home`, `JAVA_HOME` or the PATH.
- The IntelliJ plugin uses a hand-written `PsiBuilder` parser over the ANTLR lexer instead of an ANTLR-to-PSI adaptor, for error recovery while typing.
- Java sees `.axl` files through light classes whose member types come from the in-memory translation parsed as Java; members navigate to the `.axl` declarations.
- javac and NullAway errors in IntelliJ come from `axl check` run in a separate JVM (the IDE's JVM lacks the options Error Prone needs) and appear after a save; in Ultimate the language server reports them instead.
- In Ultimate the language server provides diagnostics and hover only; completion, navigation and highlighting stay with the plugin's PSI so that the two do not duplicate each other.
- The platform has no extension point to hide local variables in the debugger, so the translator's `$` locals are labeled "Axolotl internal" instead of hidden.
- `fn main()` runs through IntelliJ's Java application run configuration for the generated class; building is left to Gradle or Maven delegation.
- The project builds with Gradle 9; the Gradle plugin it publishes still supports Gradle 8.5 and newer, which a functional test checks.
- `try` binds like a unary operator (`try a + try b` is `(try a) + (try b)`); in stage 1 it took the whole expression to its right, which made no difference in the two statement forms allowed then.
- Lifted `try`: operands to its left that are not literals, lambdas or the file's own names are kept in `$t` temporaries; `&&`/`||` with `try` on the right become `boolean $t = false; if (left) { ... }`, so that a null check on the left still covers the right, and an `if (a && try b)` without `else` becomes nested `if`s; `?:` becomes `T $t = left; if (Objects.isNull($t)) { ... }`, with `T` from the written type of the `val` or the function when there is one; a `while` condition is evaluated inside `while (true)`.
- `try` after `?.` stays an error: the expansion would need the rest of the chain inside a conditional, and moving the `try` into a `val` is clearer.
- Pipes support `filter`, `map`, `peek`, `sorted`, `distinct`, `limit`, `skip`, `forEach`, `anyMatch`, `allMatch`, `noneMatch`, `count`, `first` and `mapResult`; without an ending stage the result is `toList()`. A lambda of a stage without parameters takes `it` even if the body does not use it.
- `mapResult` expands to a loop over a `$p` list. The runtime has no helper and the translator no types, so the element type comes from the `val`'s written `List<T>` or from a same-file function returning `Result<T, E>` (AXL009 otherwise).
- `a!!` expands to `java.util.Objects.requireNonNull(a)`, so the exception points at the assertion and NullAway treats the result as non-null.
- Top-level `val` types are inferred in two steps: local rules for literals, operators, constructor calls and same-file functions; for the rest, javac attributes a `$infer` method in a draft translation of the whole module (unknown types replaced by `Object`) and the inferred type is written into the generated field. Generated Java never contains `var` at class level.
- NullAway trusts JDK generics: it does not check what a lambda returns to a JDK functional interface, the `?` of type arguments such as `List<String?>`, or the declared types of locals. A javac `TaskListener` started by the `AxlDiagnostics` plugin (`NullChecker`) checks these in generated classes; it reports only what NullAway cannot see, so one problem gives one error. NullAway sometimes sees more than the checker assumes (a `List<String?>` written out in a type), so a report that overlaps an error of NullAway on the same line is dropped. javac drops type annotations when it infers types, so the checker follows the `?` of type arguments through `var` locals, `new` and stream calls by itself. Its reports wait for the end of the compilation, because Error Prone skips its analysis once there are errors.
- The JDK's functional interfaces say nothing about null, so a lambda passed to one may not return null unless the type argument has `?`; `Map.computeIfAbsent` and the other `Map` methods allow it for a value type with `?`, and `Optional.map` always does.
- JDK methods that throw on a null argument are listed in `NullChecker` by the class of the receiver: the `String` methods that take a string, `String.format` (but not its locale), the `StringBuilder` and `StringBuffer` constructors and their `indexOf` and `lastIndexOf`, `compareTo` of strings and boxed numbers, `TreeSet`, `ArrayDeque`, `PriorityQueue`, the concurrent queues and deques, `ConcurrentHashMap`, `ConcurrentSkipListMap` and `ConcurrentSkipListSet`, `Hashtable` and `Properties`, `Pattern.compile`, `Path.of` and `Paths.get`, and the keys of `TreeMap`; `contains`, `indexOf` and `get` of `List.of` and the like when called on the factory directly or on a `val` that holds such a collection. Method references to these methods are checked the same way, and `collect(Collectors.toCollection(TreeSet::new))` does not take nullable elements for a collection whose `add` is in the table. The list is a table rather than a rule because Java's documentation, not its types, says which parameters reject null; a collection whose static type is an interface is not checked, since `contains(null)` throws only for some implementations.
- JDK methods that return null when there is no value (`Queue.poll`, the previous value of `Map.put`, `Map.computeIfPresent` for a missing key, `AtomicReference.get`, `getAndUpdate`, `getAcquire` and the like) are listed in `PlatformValues` by declaring type, name and parameter count, and found in overrides through the supertypes. NullAway's library models leave them out, since they return null only in some states; a table keeps the decision explicit, and `getFirst`, `element` and `pop`, which throw instead, are not in it.
- A raw type that Java code gives (`List raw()`, `Collections.EMPTY_LIST`) cannot be stored, passed or returned where Axolotl writes type arguments: javac converts it with only an unchecked warning, and a wrong element fails later with a `ClassCastException`. `NullChecker` reports it as AXL100 from inside the plugin rather than through `-Xlint:unchecked`, so the check does not depend on the javac options a build tool passes.
- Strict null mode is off by default: without it the rules match NullAway's, which trusts unannotated code. The same checker does it (plugin argument `strict`) and checks only generated classes, so mixed Java sources are unaffected.
- Strict mode trusts JDK constants (`System.out`), constants, the Axolotl runtime, `Objects.requireNonNull*`, string, number and `Math` methods, the immutable collection factories, `toString()`, `@NullMarked` code and members annotated `@NonNull`/`@NotNull`/`@Nonnull`; everything else returned from Java is nullable until checked. A lambda kept in a value of a JDK interface type gets nullable parameters, since any Java code may call it. Narrowing follows the same rules as NullAway: `!= null`/`== null` checks, `&&`, `||`, early exits, `while` conditions; a loop body is scanned until the nullable values it leaves settle.
- NullAway also narrows fields and call results after a null check and keeps them narrowed across calls, which may set them to null. The checker narrows only locals, parameters and `val` properties (final fields reached through final fields from a local that is not assigned again), and reports a use of a nullable `var` property or call result that only NullAway's narrowing allows.
- javac's most common messages (unknown names, type mismatches, wrong arguments, missing returns) are reworded with Axolotl type names; the rest are shown as javac prints them. NullAway's nullable argument message becomes AXL102 like a dereference.
- The Maven build of the plugin removes `org/axl` from its build-local repository first, because Maven would otherwise keep using the copies of the modules it resolved in an earlier build.
- The runtime is `@NullMarked`, so NullAway checks the value types of `Result`: `Ok(null)` does not fit `Result<String, E>`. `Result.mapErr` converts the error type for `try`.
- `a ?: b` passes its fallback as `Nulls.Fallback`, a null-marked interface, because NullAway does not check what a lambda returns for JDK interfaces such as `Supplier`; a number on the right is passed directly (`Nulls.or(a, 0)`) so that Java widens it to `Long` or `Double`, with overloads for primitive, boxed and other (`Number`, `Object`) left sides. After `?.` the left side is moved into a temporary first, so that Java can type it. With `--inline-elvis`, a `?:` between two different kinds of boxed numbers keeps the `Nulls.or` form, because Java would unbox both sides of the conditional.
- A pipe's `map` lambda is wrapped in `Nulls.nonNull`, which makes NullAway reject a `map` that may produce null; where the list it builds goes to a type written with `?`, such as `val xs: List<String?>`, it is wrapped in `Nulls.nullable` and may produce null.
- A `?.` chain passed as an argument is moved into a temporary first: as an argument, the result type of `Nulls.map` would come from the parameter, which makes overloads such as `println` ambiguous. Where no statement can go (one-line lambdas, top-level values, `attempt`), it is passed as `Nulls.typed(...).value()`, whose receiver Java types before it picks an overload.
- `|> first` is `Nulls.first(stream.iterator())`: `findFirst` throws on a null element, and an iterator argument keeps the call out of overload resolution.
- Operands to the left of a lifted `try` keep Java's order, including the receiver of a call, the receiver of a method reference, the object of an assigned field and the value a compound assignment reads; class and package names (also nested ones such as `Thread.State`) are not copied, and `Ok(x)`, `Err(x)`, diamonds and factories such as `List.of(...)`, `Optional.empty()` and `Comparator.naturalOrder()` stay inline with their arguments copied, so that Java infers their type arguments.
- A stage lambda nested in another lambda that has `it` is an error (AXL004): Java forbids a lambda parameter that shadows another, and renaming `it` would surprise readers.
- `java` and `axl` cannot name locals or files, `System`, `Nulls` and `Result` cannot name values, and `args` cannot name a local of `fn main()` or a top-level value of its file, because the generated code uses them; files cannot be named after the classes the generated code uses (`Nulls`, `Result`, `Ok`, `Err`, `System`, `Nullable`, `NullMarked`, `String`, `Integer`, `Long`, `Double`, `Boolean`, `Object`, `Exception`).
- Generated Java keeps the line breaks of long expressions, so each operand, argument, chain step and pipe stage maps to its own .axl line.
- Top-level values are checked for reads of later values, also through functions of the file, lambdas and function references passed to calls, values that hold a lambda, and `Main.x` (AXL016), because they are static fields set in order. Values of two files that read each other are reported by the javac plugin, which sees all classes.
- In a call `a < b, c > (d)` is read as two comparisons unless the names between `<` and `>` look like types (start with a capital letter).
- Incremental builds translate again every file with inferred top-level values whenever any file changes, and the other files of the package of a changed or removed file, since the declarations a file reads from other files (an interface it implements, a data class it takes apart, a function it calls) are looked up within its package; the unchanged files are read but not written, and so are the main `.axl` sources for the tests and, in Gradle, the sources of the projects a source set depends on, the module notion of the language server. Maven keeps its state in `target/axl/*.state.json` and redoes everything when options, the plugin, the classpath or the Java sources change. Both read all files on every build to reject duplicate classes.
- The parser tries SLL prediction first and falls back to LL only for input SLL cannot handle; the line predicates made LL prediction quadratic on long expressions.
- `axl run` lets the program's other threads finish instead of calling `System.exit` after `main`. Its work directory stays while the program runs, because a shutdown hook would race the program's own hooks; the next `axl run` removes the directories whose lock file is free.
- macOS packages carry the major version plus one (0.1.0 is packaged as 1.1.0, 1.0.0 as 2.0.0): jpackage rejects a bundle version that starts with 0, and keeping the offset after 1.0 keeps bundle versions growing, so that the installer never takes a newer release for an older one. The file name of the package and `axl --version` show the real version.
- A `?:` whose fallback has a known type is written `Nulls.<String>or(...)`: without the type, NullAway infers nested fallbacks again at every level, which takes exponential time. A chain whose left sides share one nullable type and whose last fallback has none, such as `a ?: b ?: "z".trim()`, is nested to the left, `(a ?: b) ?: "z".trim()`, which gives the same value and stays linear. Where the types are unknown, such as `?.` results on both sides, compile time still grows quickly: about ten nested `?:` over `?.`, or eight nested `if` values with `?:` branches, take tens of seconds. Long `?.` chains grow quadratically; forty steps cost about a second.
- A type parameter without a bound is `T extends @Nullable Object`, so `Pair<String, Int?>` is allowed and a `T` value may be null inside; `T : Object` is Java's plain `T` without null. A type test on a generic data class gets the type arguments its supertype passes on from the subject when they can be told, and takes the record apart, `Some(var v)`, when they cannot, as `Ok` and `Err` always are: a raw pattern would read the fields as Objects.
- The translator reads the declarations of the other `.axl` files of the build (parsed once more, cheaply) instead of asking javac: the fields of a generic data class, what a function returns and the values an interface requires are matters of syntax. The language server gets them the same way when it has the module's files.
- A class extends a Java class by calling its constructor after the colon, `: Thread("w")`; a supertype without parentheses is an interface. Classes written in Axolotl stay final: inheritance between them would need `open` and constructor chaining, and interfaces with methods plus composition cover what it is used for. A class that extends a Java class calls that class's methods with `super.m(...)`, which subclassing a Java reader or writer needs; it is checked to stand only before a call, in such a class, for methods of that class.
- An enum carries fields given by each constant and methods after the constants, which all of them share, and may implement interfaces. Java libraries put behavior on enum constants (`CSVFormat.Predefined.getFormat()`, a `Supplier`) and their tests call it, which a function over the constants cannot stand in for; the methods read the fields as in a data class body and need no inheritance. Constant bodies and abstract methods stay out: a field each constant gives says what differs, and a `when` over the constants stays exhaustive.
- A data class body holds methods only, for `Comparable` and the interfaces with methods it implements; other behavior over data stays in functions, where `when` over a sealed interface is exhaustive.
- `break` and `continue` have no labels, cannot leave a lambda and cannot leave a `when` that gives a value, which is a Java switch expression. A `break` inside a `when` statement in a loop names the loop in the generated Java (`loop$1: for (...)`, `break loop$1;`), since Java's plain `break` would leave the switch the `when` becomes; a loop no such `break` leaves gets no label, and `continue` needs none.
- `use (val r = open()) { ... } else e -> h` is try-with-resources with a catch of `Exception` for the `else`; without `else` a resource whose `close()` declares a checked exception is an error, since an Axolotl function cannot pass it on. The handler is a call or a `throw`, as for a statement `attempt`, and `use` is a contextual keyword (an identifier followed by `(val`), so values named `use` still work.
- A lone `attempt` with a call or `throw` as handler is the statement of a lambda, so `Thread({ -> attempt Thread.sleep(1L) else e -> log(e) })` works; in a pipe stage that gives a value, such as `map`, it is the value instead. `return attempt ...` in a block lambda gives the value elsewhere.
- The exit of a statement `attempt` is a statement of its own, not an expression, so it can only stand in the `catch` of an `attempt` on a line of its own. It reuses the checks of `break`, `continue` and `return`. `return` in a lambda returns from the lambda, as it does elsewhere. The exit has no braces, `use ... else` and `when` arms do not take it. An `attempt` does not exit, only its handler does, so code after it is reachable.
- Error Prone's AlreadyChecked is off: it throws on the `var` of a record pattern inside an `if`. ReferenceEquality is an error, NarrowingCompoundAssignment an error, AlwaysThrows a warning that the messages make an error again outside `attempt`.
- A generic sealed type that comes from a jar or class directory on the classpath is narrowed by `is` with its type arguments, like one of the build: the translator reads the type parameters, supertypes, record components and permitted classes of compiled classes (and of Java sources and the JDK) through javac (`JavaClasses`, `JavacClasses`). The language server and the build tools give it their classpath; the IntelliJ plugin reads the module's classpath from the IDE's Java model (libraries, the Java sources of the module and of the modules it depends on, and the module's JDK), and only the JDK while it indexes. The type must be a direct supertype of the tested class; a class that reaches the sealed type through another class is narrowed raw, and so is a type of another package of the same build, whose class does not exist yet.
- `axl check`, `axl build` and `axl run` hand their compilation to a daemon per user and installation, as Gradle and Kotlin do, because loading and warming javac, Error Prone and NullAway costs 2 to 3 s against 0.1 to 0.5 s for compiling a small program. It is reached over loopback TCP with a random token in a file readable only by the owner; its directory name carries a fingerprint of the jars, Java and the JVM settings that change what a build writes, so incompatible launchers never share a daemon. It compiles one job at a time with a fresh javac per job and keeps no javac state; it caches no translations, which are a few percent of a build and would need every sibling file and the classpath in the key. The program of `axl run` runs in the launcher's JVM, so that `System.in`, `System.exit`, threads and statics stay the program's own. Whenever the daemon cannot do a job the launcher compiles in process, which prints the same output. On Windows a child process inherits its parent's handles, so the daemon is used only from a console.
- Arrays stay out of the language: lists are the collection. Two gaps in Java interop are closed with the smallest additions. A list goes where Java takes an array of objects: the translator reads the parameters of the called method from the classpath (`JavaClasses.signatures`) and passes `xs.toArray(new T[0])` only when every overload with that many arguments takes an array of a class at that place; overloads that take a collection, `Object...` varargs (where a list is one value), type-variable and primitive arrays get no conversion, so nothing a Java call could already mean changes meaning. For buffers, `ByteArray(n)` and `CharArray(n)`, the Kotlin names, create `byte[]` and `char[]`; the two names are also types, reserved like `Int`. Element access stays with Java (`ByteBuffer.wrap`, `String(...)`, `Arrays`). `IntArray` and other arrays keep the 'Axolotl uses lists' answer. Rejected: array literals or an `Array<T>` type (a second collection), and a runtime `bytes(n)` function (a default-imported lowercase name collides with common local names).
- An `is` test that narrows nothing writes `Ok<?, ?>`, so the generated class names none of the subject's types. A caught `InterruptedException` sets the thread's flag again before the handler of `attempt` or `use` runs, so interruption still stops a worker.
- A pipe source whose type the translator does not know is passed to `Nulls.stream`, overloaded for `Collection` and `Stream`, so that javac picks the right one. `Result.propagate` takes `Result<T, ? extends E>`, so `try` passes on errors of a subtype of the function's error type. A list passed as an array of a generic class is passed as `Nulls.arrayOf(list, Element.class)`, whose result javac types from the list; other arrays use `toArray(new X[0])`. The checker reads the permitted classes of sealed types and the constants of enums of the classpath through `JavaClasses` to check that a `when` covers them; a class the build declares is never judged from the classpath.
- The formatter lays out the tokens of the compiler's lexer instead of printing the syntax tree, so that comments and line breaks are kept. It never moves a token to another line, because a newline ends a statement; it changes spaces, indentation, the number of blank lines and the order of imports. A line that continues an expression keeps its indentation relative to the line where the statement starts, but at least 4 spaces. Top-level declarations are separated by one blank line, except that declarations of one line each may stand together. Imports form one group sorted by qualified name. Empty braces are `{}`; braces of lambdas have spaces inside. The check after formatting compares the syntax tree without positions and the generated Java with its imports sorted.
- A port of Apache Commons CLI showed what an Axolotl class cannot give Java callers: subclassing, arrays and varargs in signatures, `throws`, `transient`, casts, bounded wildcards, `char`, `protected` and package-private members. They stay out. Each would bring back a part of Java that the language removes on purpose (inheritance, arrays, checked exceptions, unchecked conversions, a second kind of character, a second kind of type argument), and each is needed only at the edge of a library, where a small Java interface with default methods adapts the class. The port did take two small additions for the edge, private class parameters and constructors that delegate to the first one, because without them every field set by a constructor is public and a class has one way to be created.
- A class parameter may be `private`: a private final field set by the constructor and read only by the class. A property could not stand in for it, because properties read only public parameters, so state that only the class should see was impossible. Data classes stay records with public components.
- A class may declare `constructor(...) = this(...)`: another Java constructor that only delegates to the primary one. Java libraries have several constructors, some deprecated, which factories cannot offer Java callers. Allowing only delegation keeps one place where fields are set, with no body that would bring back questions of initialization order. The arguments see only the constructor's parameters because Java runs `this(...)` before the fields are set. Overloads with the same erasure are a checker error, since Java cannot tell them apart.
- `else e: IOException ->` catches one class, as a Java `catch` does, so the everyday `catch (IOException e) { throw new UncheckedIOException(e); }` can be written and other exceptions are no longer swallowed. Statements become a real `catch`. The value form passes the class to `Result.attempt`/`Result.orThrow`, whose body is a `ThrowingCall<T, X>`, so javac still rejects other checked exceptions. One class per handler, with no multi-catch, keeps one handler per `attempt`.
- The constructor a class's parameters make can be `private` or annotated with Kotlin's `class Parser private constructor(...)` / `class Builder @Deprecated constructor()`. Java libraries keep the constructor that sets every field private while public ones delegate to it, and deprecate the constructor of a class without parameters; neither was possible, since the header's constructor was always public and a second constructor without parameters is the same Java constructor. A plain `constructor` there stays an error because it adds nothing. Data classes and enums keep their own constructors (a record's and an enum's).
- A private `val` class parameter that only property values and the superclass's arguments read gets no field: Error Prone reports such a field as never read, and Java libraries keep a constructor argument they only check or convert. It keeps its field whenever a method, a written lambda, another constructor, an interface value, an annotation or a read of that member through `this` in the class, or through a value of the class or of a type the translator does not know, needs it, when nothing reads it (so the "never read" warning stays), and when it is a `var`.
- Counting loops are a form of the `for` header, not range values: `for (i in 0 until n)`, `1..n`, `n downTo 0`, with `step`. Algorithms ported from Java count all the time, and with a `while` the step had to be repeated before every `continue`. They translate to a plain Java `for` with no runtime object; a bound that may change is read once into a temporary, the step is checked once, and an inclusive end the variable could step past is reached exactly and ends the loop through a flag in the update clause, as Kotlin does.
- A sealed interface may be implemented in other files of its package. Implementations nested in the interface changed the Java names that Java callers import, so a type in a file of its own name keeps its top-level name and the interface lists it with `permits`, which Java needs across compilation units. A type of another package that implements it is an error.
- The members of a private type are public in the generated Java, because the rest of the file reads them. Error Prone's EffectivelyPrivate would report each one, so private types carry `@SuppressWarnings("EffectivelyPrivate")`; package-private members would break the methods that implement interfaces.
- Public functions, methods and constructors check their non-null reference parameters on entry with `Nulls.param(x, "x")`, as Kotlin does. NullAway only checks callers marked `@NullMarked`, so plain Java code could pass `null` into a non-null parameter, and the failure came later deep inside Axolotl code that trusted the type. One helper keeps the generated Java short: it reads the method name from the stack only when the check fails, and starts the trace at the Axolotl method; a JMH benchmark shows no cost. Private code is not checked, since only Axolotl, whose calls the compiler checks, can call it. Java 21 allows no statement before `this(...)` and `super(...)`, so a parameter passed on unchanged is checked inside the argument and any other after the call.
- A constructor may pass its values to another constructor of its class with `this(...)`, chosen as Java chooses an overload, by number and types. Libraries chain their constructors, and spelling out every value in each repeats the defaults. Cycles are an error, from the checker where the number decides and from javac where the types do. Constructor work stays with properties set in order; there is no init block.
- `use (expr) { ... }` without `val` gives the resource a generated name, for locks and scopes the block never reads; Java 21 has no unnamed variables. `use` before parentheses that a block follows is the statement, so a call `use(x)` still works.
- A typed handler of a checked exception compiles whether or not the code declares the class, as a statement as well as a value. Axolotl functions pass checked exceptions on undeclared, so code that wraps an Axolotl library needs `else e: IOException ->`, which javac rejected as never thrown. The generated `try` starts with `Result.mayThrow(IOException.class)`, a no-op that declares the class, so the catch stays a plain `catch (IOException e)` and other exceptions pass through unchanged.
- `Character(code)` turns an `Int` into a character, as Kotlin's `Char(code)`: `Reader.read()` gives character codes, and without casts the Commons CSV port wrote `Character.toString(Math.floorMod(c, 65536)).charAt(0)` 22 times. It fails for a number outside 0..65535, as `Math.toIntExact` does for a `Long`, so the -1 of the end of input is never taken for a character. The reverse needs nothing: a `Character` widens to its `Int` code where one is expected.
- javac infers type arguments without `?`. NullChecker follows the written type arguments of the arguments, and what a lambda returns for a type variable that the JDK method's result holds, such as `R` of `Stream.map`; NullAway's error for a value whose only problem is a missing `?` waits for that result. Inside a class, a local set from a call takes the written result type of the method, also of other types of the package and of JDK methods with a primitive result, so a `when` over an `Int` and `==` on two `Character`s compile as in a top-level function.
